## 1. ROOT CAUSE ANALYSIS

### `/api/auth/login` → HTTP 400
**No request/schema mismatch exists.** The frontend posts exactly
`{ email, password }` (`frontend/src/api/api.js` → `loginUser`) and
`server/routes/auth.js` validates the same two fields. The 400 is the route's
correct, deterministic rejection:

- absent / non-string / over-length fields → `400 "Missing email or password"`;
- unknown user, blocked user, or wrong password → `400 "Invalid credentials"`.

In the observed production the 400 is the second case: `render.yaml` sets
`SEED_DEMO_USERS=false` and admin bootstrap only runs when `ADMIN_TEMP_PASSWORD`
is set, so no pre-created account exists for a first-time login. This is correct
security behaviour (a unified message prevents account enumeration) and was left
intact. Verified locally against the real route module (stubbed DB): empty body,
non-string fields, missing password, and over-length email all return
`400 {"error":"Missing email or password"}` before any database access.

### `/api/ai/health` → HTTP 502
The gateway's status proxy (`server/routes/ai.js` → `proxyStatus`) answered any
**non-JSON** upstream body with a blanket `502 INVALID_UPSTREAM`. A Render
free-tier spin-up page (`503` HTML "Application loading"), a wrong/retired
service URL, or a Cloudflare HTML challenge all collapse into that one generic
502. The `.env.example`, `server/.env.example` and `DEPLOYMENT.md` still
hard-coded the **retired single-service host** (`edunova-ai-o2vy.onrender.com`,
the old in-process v4 build) as `AI_ENGINE_URL` — in the split architecture that
variable must point at the **`edunova-ai` orchestrator** (no model), which
`render.yaml` already wires automatically via `fromService`.

**Fix:** classify the non-JSON upstream by its HTTP status — `503` → retryable
`MODEL_NOT_READY`/`starting`, `404` → `CONFIG_FAILED`, `504` → `UPSTREAM_TIMEOUT`
— and remove the stale host from the example configuration.

### `/api/ai/chat` → HTTP 429
429 originates from exactly two correct paths: (1) the Express per-user token
bucket (`AI_RATE_LIMIT_MAX_REQUESTS=20` / 60 s) and (2) the inference service's
single-flight admission (`MODEL_BUSY`). While the model was starting, repeated
"Try again" clicks each counted against the bucket and eventually triggered the
real rate limit. **No misclassification exists**: a not-ready model is `503
MODEL_NOT_READY`, never 429. Rate limiting was deliberately left unchanged.

### Frontend `MODEL_NOT_READY`
This is the correct rendering of `errorStage=MODEL_NOT_READY` (503) from the
readiness gate. The model never reached READY in production because the live AI
service was still the **old v4 in-process build** (512 MiB / 0.15 CPU, ~0.2
tok/s per the repo's own production observations), not the new split
`edunova-inference` service. The current code reaches READY — proven locally with
real llama.cpp 0.3.35 (full lifecycle `BOOT → … → READY`, warmup + real
inference test both pass).

## 5. 510 MB VERIFICATION

`TOTAL_FOOTPRINT = MODEL_BYTES + RUNTIME_BYTES + TOKENIZER_BYTES + PROCESS_BASELINE + KV_CACHE + TEMP_BUFFERS + INFERENCE_OVERHEAD`

Using the deployment gate in `inference/resources.py` (`estimate_requirement`):

```
model weights (Q4_K_M, mmap)        101 MiB
KV cache @ 2048 (30L, 3KV x 64)      45 MiB
llama.cpp runtime + compute buffers 140 MiB
FastAPI parent + supervised worker  110 MiB
safety margin                        64 MiB
---------------------------------------------
TOTAL REQUIRED                      460 MiB   (catalogue pre-download: 447 MiB)
```

**460 MiB ≤ 510 MiB — PASS.** Recommended instance size: 512 MiB (Render Free).
This sits slightly above the *preferred* ≤450 MiB target but comfortably inside
the 510 MiB absolute ceiling; closing the last 10 MiB would require shrinking the
context window or the safety margin, both of which trade away product quality or
OOM headroom and were deliberately not done.

## 10. REMAINING RISKS (honest)

1. **Real-model quality/latency is unverified in this sandbox** — HuggingFace is
   unreachable, so the real SmolLM2 GGUF could not be downloaded. The pipeline
   (load → warmup → inference → streaming → JSON grammar) is proven with real
   llama.cpp; the actual answer quality must be confirmed on the deployed
   `edunova-inference` instance once it pulls the weights at runtime.
2. **Production env must be repointed** — if an operator override still points
   `AI_ENGINE_URL` at the retired `edunova-ai-o2vy` host, `/api/ai/health` will
   again return a proxy page (now honestly 503/`CONFIG_FAILED` instead of 502).
3. **Footprint headroom** — 460 MiB required leaves ~50 MiB under the 510 MiB
   ceiling; it is above the *preferred* 450 MiB. Reducing it further would
   require a smaller model or context, at a quality cost.
4. **Concurrency = 1** — the single-flight inference serializes simultaneous
   students; a concurrent burst queues behind `MODEL_BUSY` (429). This is the
   safe default and was not relaxed.
5. **Mongo/DB-backed tool paths** were exercised only via unit/integration
   stubs here (no live MongoDB); the Mongo integration tests remain skipped
   without a `MONGO_TEST_URI`.
